### High: default Docker deployment has no application auth and exposes root/root database

Evidence:

- `api/auth.py:30-33` skips authentication entirely when `OPEN_NOTEBOOK_PASSWORD` is unset.
- `docker-compose.yml:15-30` exposes the app/API and sets SurrealDB credentials to `root` / `root`.
- `docker-compose.yml:6-7` exposes SurrealDB port `8000` on the host.
- `docker-compose.yml:20-30` does not set `OPEN_NOTEBOOK_PASSWORD` or `CORS_ORIGINS`.
- `api/main.py:163-169` warns that missing `CORS_ORIGINS` allows all origins.

Impact:

Anyone who can reach the exposed ports can use the API/UI without an app password and may also reach the database service with documented default credentials. This is acceptable only for a tightly local developer setup, but the compose file is user-facing and uses `restart: always`/published ports, which makes accidental LAN or server exposure plausible.

Recommended fix:

- Require `OPEN_NOTEBOOK_PASSWORD` in the production/user-facing compose example, preferably via secret file.
- Bind SurrealDB to localhost or keep it on the Docker network only unless explicitly requested.
- Replace default database credentials and default encryption key with required user-provided values or a generated `.env` setup step.
- Set `CORS_ORIGINS` explicitly in deployment examples.

### Medium: source download path guard uses unsafe raw prefix checks

Evidence:

- `api/routers/sources.py:597-604` checks `resolved_path.startswith(safe_root)`.
- `api/routers/sources.py:617-624` repeats the same raw prefix check for file availability.
- The upload creation path is stricter at `api/routers/sources.py:337-344`, using `str(uploads_resolved) + os.sep`.

Impact:

The download guard accepts paths whose string prefix matches the uploads directory but are not actually inside it, such as `data/uploads_evil/file`. The normal upload path blocks this, but legacy records, migrations, command failures, or direct database edits could put such a path on a source asset and make `/api/sources/{id}/download` serve it.

Recommended fix:

Use `Path(resolved_path).resolve().relative_to(Path(UPLOADS_FOLDER).resolve())` or `os.path.commonpath([safe_root, resolved_path]) == safe_root` in both download and availability checks. Add regression tests for sibling-prefix paths.

### Medium: backend type-check gate is declared but not reliably runnable

Evidence:

- `Makefile:36-37` defines `lint` as `uv run python -m mypy .`.
- CI uses `uv sync` without extras in `.github/workflows/test.yml:23-29`.
- After `uv sync`, `uv run python -m mypy .` failed with `No module named mypy`.
- Running `uv run --extra dev python -m mypy .` installed mypy and then reported 82 errors across 19 files.

Impact:

The repository advertises a type-check command that is not installed by the default development/CI dependency path, and once installed, it is not passing. This makes `make lint` unusable as a gate and lets typing regressions accumulate.

Recommended fix:

- Add `mypy` to `[dependency-groups].dev` or change docs/Makefile to use `uv run --extra dev`.
- Decide whether mypy is intended to be enforced. If yes, fix or baseline the current 82 errors and add the gate to CI.

### Medium: frontend npm audit reports unresolved vulnerabilities

Evidence:

- `npm audit --json` reported 6 vulnerabilities: 1 high, 4 moderate, 1 low.
- High: `ws` memory exhaustion DoS, affected range `8.0.0 - 8.20.1`.
- Moderate: `postcss` XSS advisory via `next`; npm recommends a semver-major Next change, so this needs manual dependency review.

Impact:

Some findings may be development-only or transitive, but `next` is a production dependency and should be triaged. The high `ws` advisory is also worth addressing even if only present through tooling.

Recommended fix:

Run a targeted dependency update pass, review `npm audit fix --dry-run`, and avoid `npm audit fix --force` until the Next downgrade/major-change recommendation is understood.

### Low: frontend lint passes with warnings that can hide stale UI behavior

Evidence:

- `npm run lint` produced 12 warnings and 0 errors.
- Most warnings are missing hook dependencies around translation functions and query arrays.

Impact:

These are not release blockers, but stale translations or memoized data can appear after language or query state changes.

Recommended fix:

Clean up the hook dependency warnings and unused imports, then consider making lint warnings fail in CI once the backlog is zero.
